# Browser sweeps

The checks run in a real browser before each checkpoint (docs/plans): what happy-dom can't measure (color contrast, layout overflow, focus indicators, D-pad movement).

```sh
bunx playwright-core install chromium      # once
bun scripts/sweeps/pages.ts [platform] [query]   # axe + overflow + page errors
bun scripts/sweeps/keyboard.ts [platform]  # Tab through every page; every stop shows focus
bun scripts/sweeps/dpad.ts                 # every TV focusable is reachable by arrows

bun scripts/sweeps/server.ts [pages|keyboard]    # the server's real admin pages (no prototypes needed)
bun scripts/sweeps/compare.ts [folder]           # every admin screen beside its prototype, for review
bun scripts/sweeps/playback.ts [chromium|firefox] # the web player in real browsers (also in CI)
bun scripts/sweeps/phone.ts [highsea.app]       # the client on an iPhone simulator, through Maestro
bun scripts/sweeps/tv.ts [screen ...]             # the client's D-pad walk on an Apple TV simulator, an XCUITest on the remote
bun scripts/sweeps/layout.ts build [phone|tv|both] # apps/client's Release mock-mode builds, on the simulators
bun scripts/sweeps/layout.ts [folder] [--preflight] # apps/client's screens the same on the web, the iPhone and the Apple TV
```

`server.ts` builds the server (`next build` in `apps/server`) and boots the production build on port 3150, as the image runs it; `SWEEP_DEV=1` boots Next's development server instead and skips the build. It runs under the Node in `.nvmrc` (it stops first if `node` is another version), with throwaway folders. It sweeps setup step by step, then finishes setup and adds people, an API key, a custom theme and a waiting TV through the API, then grabs two releases from the fake indexer (blocklisting one), adds a magnet by hand and leaves a stray file for manual import. For subtitles (checkpoint 7a) it signs OpenSubtitles.com and Subdl in against their fakes (`HIGHSEA_SUBTITLES_FAKE=1`), and imports Sintel and Nosferatu from generated clips, Sintel with an English sidecar, so A6's Subtitles tab and A10's Wanted list have something to show. The server runs with `HIGHSEA_TORRENT_OFFLINE=1`, so the torrent engine opens no sockets: grabs join the queue as Queued, and nothing downloads or reaches the network. Then it checks every admin page signed out and signed in, the same way as `pages.ts` and `keyboard.ts`. It also counts React's `console.error` warnings (hydration mismatches, for one) as problems. `SWEEP_PORT` moves it, and `SWEEP_SHOTS=<folder>` also saves each page in the default theme at each width. With `SWEEP_DEV=1` the first run is slow, because Next compiles each page the first time it's opened.

`compare.ts` (checkpoint 9c) boots the same seeded server from the production build on port 3160 (`COMPARE_PORT`; `COMPARE_DEV=1` for the dev server) and starts the prototypes if nothing answers on :4500. For each row of checkpoint 9's review matrix it opens the prototype's state and the server's equivalent at 1440 and 390 in the default theme, opening the same tab or dialog on both sides, and saves both. The folder (a new temporary one unless given) gets the PNGs, `index.html` with each pair side by side, and `checklist.md` in the same order for the owner's review. A pair it couldn't open is listed at the end and in the checklist.

- **localhost:** it browses `localhost`, because Next's dev server serves its dev scripts to that origin only (it matters with `SWEEP_DEV=1`).
- **One browser context per page:** a signed-in page holds the event stream open, and Chromium allows six HTTP/1.1 connections per host.
- **No `networkidle`:** for the same reason it never arrives. A page counts as ready once React has hydrated it and nothing is `aria-busy`.

`playback.ts` (checkpoint 4.2b) builds the server and the web app, boots the same seeded server on port 3140 (`PLAYBACK_PORT`) and adds Big Buck Bunny as an MP4 remux of the seed's clip. Then, in Playwright's Chromium and Firefox (`bunx playwright-core install chromium firefox` once), it signs in on `/web`, plays Big Buck Bunny directly and Sintel's MKV as HLS, turns on Sintel's English subtitle and waits for a cue to be drawn, seeks to 8:00 and waits for it to play on, and leaves, checking the last report and the session's end and that the server kept the place. Autoplay is allowed by each browser's documented switch, since the run opens the player by its address rather than by pressing Play. It takes about 10 seconds a browser after the builds and the seed. CI runs it on every push; Safari is tried by hand at each review.

`phone.ts` (checkpoint 4.5a) builds the server, boots the seeded server on port 3160 (`PHONE_PORT`), installs a fresh copy of the one client's iPhone build (`tv.highsea.mobile`) on the booted simulator (`PHONE_SIMULATOR` picks one by UDID), and runs Maestro's flow in `apps/client/.maestro/sign-in-and-play.yaml`: add the server by address, sign in as Theo, search for Sintel, play it until the controls hide, and go back to its page, which offers Resume. Then the server's history must show Theo's iPhone (`ios`) playing Sintel. It needs Maestro on the PATH (`~/.maestro/bin`, with Java 17 or later) and a Release build for the simulator without mock mode, signed ad hoc as `native.yml`'s ios job builds it (the command is in the script's header): an unsigned build has no keychain entitlement, so it can't keep a sign-in. It takes under a minute after the server's build. Elements are found by the labels VoiceOver reads. It runs locally only, before each checkpoint report (the owner, 2026-10-29), not in CI.

`phone-compare.ts` and `tv-compare.ts`, which put the old iPhone and Apple TV apps' screens beside their prototypes', went with those apps in B2 (one-client-platform-b.md): with one codebase the prototypes' frames hold the client itself, so `layout.ts` (below) checks that each screen is the same on the web and on the simulators, and its sheet, with `compare.ts`'s for the admin, is what the owner reviews.

`tv.ts` (checkpoint 4.5b) is the TV's D-pad walk, on the one client's Apple TV build. Maestro and Detox can't press a tvOS remote, so it's an XCUITest on `XCUIRemote` (`apps/client/dpad-walk/DpadWalk.swift`), generated with XcodeGen (`brew install xcodegen`) from `apps/client/dpad-walk/project.yml` into a scratch folder and run with `xcodebuild test` by `tv-uitest.ts`. On Home, a film's page, Search, the library, Settings and the player (paused), it walks breadth first from the first focus with the arrows, and every focus stop on the screen (each `@highsea-tv/ui` stop's test id, `tv:` and its row, then its label) must be reached, as `dpad.ts` checks the prototype's. Name screens to walk only those. It runs against the client's Release build (`tv.highsea.tv`, without mock mode, built as `native.yml`'s tvos job builds it) already installed and signed in on the booted Apple TV simulator (`TV_SIMULATOR` picks one by UDID), with a film to resume on Home, and takes about four minutes a screen. The same test's `testScreenshots` saves each of those screens into the folder `SHOTS` names, for looking at by hand. It runs locally only, not in CI.

`layout.ts` is the one client platform's check that a screen is the same everywhere ([one-client-platform.md](../../docs/plans/one-client-platform.md)). It takes `apps/client`'s Choose a server, Harbor's sign-in, the shell and Settings against the mock, on the web (the mock export in Playwright at compact-touch 402 × 874 with the iPhone's safe area, regular-pointer 1440 × 900 and tv 1920 × 1080) and on the booted iPhone 17 Pro and Apple TV simulators (an XCUITest, `apps/client/uitest/Layout.swift`, generated with XcodeGen and run by `tv-uitest.ts`'s `runUITest`, stopped after ten minutes, which dumps each screen's accessibility tree). Every capture the run asks for must be there, have nodes, hold its screen's anchor (Harbor's row, the Password field or the TV's Sign in with your phone, the You tab or the account's settings stop, the Settings title) and be its device's size (402 × 874 and 1920 × 1080 points, compared with the web 1:1, never scaled). Nodes pair by name and a kind that fits: a labelled view with no role pairs with a text, an image or a group, never a control, so a control that lost its role fails as a kind that differs. compact-touch is compared with the iPhone and tv with the Apple TV: a node that moved or changed size by more than 4 points fails, a text's size included (the run of 2026-11-03 measured every text within 1.33 points), as do a text that differs and a node on one side only, unless `EXCEPTIONS` gives the reason (iOS's scroll indicators, the live count, the TV's new pairing code). A field's drawn label, which the device reads only as the field's name, is excused only where the Field draws it: at its field's left edge, no wider, and the control spec's gap above it. A run that could compare and compared nothing fails; `--targets web` only captures. The comparison and these checks are pure (`compare`, `assess`) and tested in `layout.test.ts`. The folder (a new temporary one unless given) gets each capture's PNG and tree, `results.json`, and `index.html` and `checklist.md` with the captures side by side, each pair's differences, and the device runs' notes (a press that took more than once). It makes the mock export once and holds it for the run (`HIGHSEA_CLIENT_EXPORT=0`). `build` makes the Release mock-mode builds and installs them; it replaces `apps/client/ios` with `expo prebuild --clean`, so nobody else may prebuild or build `apps/client` while it runs (a lock in the temporary folder keeps two builds apart), and the phone's prebuild is put back after the TV's even when that fails. `--preflight` takes Choose a server only, in about a minute; `--targets web,phone,tv` and `--screens` (in the steps' order) narrow it. It runs locally only, not in CI.

- **The prototypes' sweeps serve their own build.** `pages.ts`, `keyboard.ts` and `dpad.ts` build the prototypes into a temporary folder and serve it with `vite preview` on :4510 (`SWEEP_PROTOTYPES_PORT`), so nothing needs starting first. A build loads each page about three times faster than the dev server's unbundled modules. `SWEEP_BASE=http://localhost:4500` sweeps a running `bun run prototypes` instead.
- **No fixed waits.** A page counts as loaded once its DOM has been still for 400 ms (`settle` in `lib.ts`), longer than the mock's 180 ms a call, and 1.5 s at most. The announcement is gone once Radix has removed it. Pages run as many at once as the machine has cores, less two (`WORKERS`, 2 to 12). On a 12-core Mac the three take about 5½ minutes together (pages about 4½, keyboard 1, D-pad 10 seconds); they took 40 before.
- `pages.ts` runs every route at its platform's widths in three themes, every data state, 200% text and reduced motion. On each it also checks that controls in one row share one height, corner and text size (design system 1.1, `mixedRows` in `lib.ts`): icon-only controls have no text size, chips and avatars may be round, switches keep their own track, and `data-item` and `data-player-controls` are left out ([controls.md](../../docs/design-language/controls.md)). Narrow it with a platform and one query, e.g. `bun scripts/sweeps/pages.ts web text=200`. `keyboard.ts` takes a platform too.
- **Sweep what changed.** For a fix between checkpoints, run the sweeps for the platform it touched (`pages.ts web`, `keyboard.ts web`); `dpad.ts` only when TV screens changed; `server.ts` only when the admin, `/web` or the server changed. Every sweep runs before a checkpoint report.
- `SWEEP_BASE` points at another server; `CHROMIUM_PATH` at another Chromium.
- Each exits non-zero with a line per problem.

Known false alarm: a toast caught mid-fade fails contrast. `pages.ts` waits for animations to finish before running axe to avoid it.

Known false alarm in `server.ts` with `SWEEP_DEV=1`: a page that calls `notFound()` (an admin page refused to a User, or a path that doesn't exist) can throw "Failed to execute 'measure' on 'Performance': … cannot have a negative time stamp" in development, and Next's dev overlay (`nextjs-portal`) then shows up as a keyboard stop. It's React's development-only performance tracks, an open upstream bug ([vercel/next.js#86060](https://github.com/vercel/next.js/issues/86060)); production builds don't have it.
