# 0058. The desktop app: Tauri around the web build, with the server reached through Rust

- **Status:** Accepted
- **Date:** 2026-10-29

Built at Phase 4's checkpoint 4.4a ([phase-4-checkpoint-4.md](../plans/phase-4-checkpoint-4.md)). Accepted when the owner signed off 4.4a on 2026-10-29; 4.4b's copies for a device are [ADR 0059](../plans/phase-4-checkpoint-4.md#adrs).

## Context

[ADR 0053](0053-clients-build-and-distribution.md) settled Tauri 2 around `apps/web`'s build for desktop. What it left open: how a page that the server doesn't serve reaches the server, where the device's token is kept, how the app finds servers, how it signs in with single sign-on, how it updates, how its installers are built and signed, and how a second language's dependencies (Rust's crates) come under the owner's rules.

The page in the app's window is the app's own (`tauri://localhost` on macOS and Linux, `http://tauri.localhost` on Windows), so every call to a server is cross-origin, and a server on the LAN is plain `http://`. The plan's recommendation (its question 2) was Tauri's HTTP plugin for the API and media straight from the server's address. Reading the rules before building changed that:

- **Media straight from the server** would be mixed content: a `<video>`, `<img>` or `<track>` over `http://` in a page from a secure origin is upgraded to `https://` or blocked ([MDN › Mixed content](https://developer.mozilla.org/en-US/docs/Web/Security/Mixed_content)), and a LAN server has no certificate for its IP.
- **Posters, trickplay and subtitles** are `/api` routes that need the device's token, and an element loading a URL can't add an `Authorization` header.
- **The HTTP plugin** would have the page hold the token to add it, and a token a page's script can read is what the web client was built to avoid ([OWASP › HTML5 Security › Local Storage](https://cheatsheetseries.owasp.org/cheatsheets/HTML5_Security_Cheat_Sheet.html#local-storage), ADR 0053's 4.2a section).

## Decision

- **`apps/desktop`** is a Tauri 2.12 app (`src-tauri/`, Rust 2024 edition, the toolchain in `rust-toolchain.toml`). Its window shows `apps/web` built with `--mode desktop` into `dist-desktop/`, at `/` rather than `/web` ([Tauri › Vite](https://v2.tauri.app/start/frontend/vite/)). `apps/web/src/host.ts` is the one place the page knows it's in the app (`inApp`, from `__TAURI_INTERNALS__`). The same screens serve both, and `src/desktop/` holds what only the app shows: C1 (Choose a server, signing in, Unreachable), the window's chrome and the updates.
- **The server is reached through Rust** (`src-tauri/src/proxy.rs`), which adds the device's token to every request, so the page never holds it:
  - API calls go through the `api` command, answered whole. A sign-in's answer has its token taken out and kept.
  - The event stream goes through `stream_open` and `stream_close`, its body sent to the page on a [channel](https://v2.tauri.app/develop/calling-frontend/#channels).
  - Anything the page loads by URL goes through the app's own `server` scheme ([`register_asynchronous_uri_scheme_protocol`](https://docs.rs/tauri/2.12.4/tauri/struct.Builder.html#method.register_asynchronous_uri_scheme_protocol)): `server://localhost/<path>` (`http://server.localhost/<path>` on Windows). `host.ts`'s `media()` rewrites the server's paths to it. A scheme's answer is one buffer, so an open-ended byte range is answered a part at a time (at most 8 MiB), with a `Content-Range` that says which part ([RFC 9110 § 14.4](https://www.rfc-editor.org/rfc/rfc9110#section-14.4)); media players ask in parts anyway.
  - Only `/api/` and `/stream/` paths of the current server pass. The app's CSP allows `server:` and nothing else beyond the app's own origin.
- **Tokens** are kept in the OS's own store, one per server: Keychain on macOS, Credential Manager on Windows, the Secret Service on Linux, through [keyring](https://docs.rs/keyring/4.2.0/keyring/) 4.2's `v1` mode (`keychain.rs`). The servers themselves (names, addresses, when last used) are plain app data in `servers.json` in the app's data folder (`servers.rs`). Choosing a server probes its addresses as the SDK's `ServerConnection` does: a LAN address that answers wins, else the fastest remote one.
- **The app signs in as a device** of client type `desktop`, named from the computer's own name ("Ines's MacBook Pro"), with its OS and the app's version.
- **Finding servers** is done in Rust (`discovery.rs`), both ways at once for a few seconds: [ADR 0020](0020-discovery-port.md)'s UDP broadcast and mDNS `_highsea._tcp` through [mdns-sd](https://docs.rs/mdns-sd/0.21.5/). Each server is sent to the page once, by id. macOS 15 asks the person before an app may use the local network ([Apple TN3179](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy)), and while it's refused sends fail with `EHOSTUNREACH`, which C1 shows as the prototype's refused state. `Info.plist` gives the reason (`NSLocalNetworkUsageDescription`) and lists `_highsea._tcp` (`NSBonjourServices`).
- **Single sign-on** opens the server's provider in the system browser and comes back through `highsea://oidc`, as [RFC 8252](https://www.rfc-editor.org/rfc/rfc8252) has native apps do (§§ 7.1, 8.12), with PKCE ([RFC 7636](https://www.rfc-editor.org/rfc/rfc7636)) so only the app that started it can finish it (`oidc.rs`; the server's side is [ADR 0024](0024-two-step-passkeys-and-tvs.md)'s 4.4 section). `highsea://connect?server=…` opens C1 with that server. Links reach the running app through the [deep-link](https://v2.tauri.app/plugin/deep-linking/) and [single-instance](https://v2.tauri.app/plugin/single-instance/) plugins.
- **Links out** (the admin, the guides, `/setup`) open in the system browser through the [opener plugin](https://v2.tauri.app/plugin/opener/), scoped to `http` and `https` URLs.
- **Playback** is the web player in each OS's webview, with a built-in profile for each ([ADR 0052](0052-device-profiles.md)'s 4.4 section). Media keys and Now Playing are the [Media Session API](https://www.w3.org/TR/mediasession/) the player already sets. WebKitGTK hands it to MPRIS since 2.38 ([its release notes](https://webkitgtk.org/2022/09/16/webkitgtk2.38.0-released.html)). WebView2 lists no media feature among its differences from Edge ([Microsoft Learn](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/browser-features)). Apple documents nothing either way for WKWebView, so macOS is checked by hand, and [souvlaki](https://docs.rs/souvlaki/) is the fallback where a webview doesn't pass it on. The owner checked it on a Mac at 4.4a's review (2026-10-29): the media keys and Now Playing work in the app, so no fallback is needed there.
- **The window** has the OS's own frame on macOS, with the traffic lights over the page (`titleBarStyle: Overlay`). On Windows and Linux it has no decorations, and the page draws the prototype's title bar (`src/desktop/window.tsx`). Its size and place are kept by the [window-state plugin](https://v2.tauri.app/plugin/window-state/).
- **Updates** come through Tauri's [updater plugin](https://v2.tauri.app/plugin/updater/) from a static `latest.json` on GitHub's Latest release, signed with highsea's minisign key. Installed apps take only updates signed with the key in `tauri.conf.json`. The repository has a development key (`apps/desktop/keys/development.key`, no password, never trusted by a release); the release key is the owner's to make, and only its public half goes in the repository (`apps/desktop/keys/README.md`). `bun scripts/release.ts desktop-key` fails while the development key is the trusted one, and a real release stops there. The plugin's `zip` feature is off: it only unpacks Tauri 1's update archives, which highsea doesn't make.
- **Installers** are built on each OS in CI, as [Tauri's pipeline guide](https://v2.tauri.app/distribute/pipelines/github/) does: one universal `.app` and `.dmg` for both kinds of Mac, an NSIS installer for the current user on Windows, and an AppImage, `.deb` and `.rpm` for x86_64 Linux. The Linux packages depend on GStreamer's good, bad and libav plugins, which WebKitGTK plays through. `.github/workflows/desktop.yml` builds them unsigned on every change; the release workflow's `desktop` job builds them signed for the updater in the `release` environment ([ADR 0050](0050-release-and-versioning.md)'s 4.4 section). The Mac app is signed and notarised once the owner has added the Apple secrets ([Tauri › macOS signing](https://v2.tauri.app/distribute/sign/macos/)). Windows stays unsigned until 1.0 (the owner's answer of 2026-10-29).
- **The Rust side keeps the npm rules:** exact versions at least two weeks old, the licence audit reading every crate on every platform from `cargo metadata` ([ADR 0009](0009-license-agpl.md)'s 4.4 section), `cargo audit` against the [RustSec database](https://rustsec.org/) in `bun run audit` (exceptions by `RUSTSEC-` id), and `cargo fmt`, `clippy -D warnings` and `cargo test` in CI on all three systems.

## Consequences

- The token never reaches a page script, and no server opens its API to another origin. In exchange, every stream passes through the app's Rust side. It's a local copy, at most 8 MiB at a time.
- The app has no code of its own for screens: a change to `apps/web` is a change to the app, and `bun run web` stays the quickest way to work on them.
- Media keys rely on each webview passing Media Session on. Linux and Windows are documented, macOS isn't, and it's checked by hand at each review until a test can drive the app.
- Tauri's WebDriver doesn't run on macOS ([Tauri › WebDriver](https://v2.tauri.app/develop/tests/webdriver/)), so the app's own flows are tested in happy-dom with Tauri's IPC mocked ([`@tauri-apps/api/mocks`](https://v2.tauri.app/develop/tests/mocking/), `apps/web/test/desktop.test.tsx`) and the Rust side with `cargo test`.
- Lose the release key and every install has to be reinstalled by hand; the owner keeps it in the `release` environment and their own backup.
- Linux arm64 and the cloud's account-linked discovery are left for later.

## 2026-10-29: the Mac app is signed ad hoc until the Apple membership

On the owner's word the first desktop release is 0.3.0, with 4.4a's app, before the owner has an Apple Developer membership. An app downloaded from the internet must be signed to run on Apple silicon, and an app without an Apple certificate is signed ad hoc, with the pseudo-identity `-` ([Tauri: macOS code signing](https://v2.tauri.app/distribute/sign/macos/)). So `bundle.macOS.signingIdentity` is `-`. Ad-hoc signing doesn't spare people Gatekeeper: the first launch is approved in System Settings › Privacy & Security, which the install guide shows. Tauri's docs don't say whether `APPLE_SIGNING_IDENTITY` wins over the config's identity, so when the Apple secrets are added the release workflow passes the identity through `--config` as well.
