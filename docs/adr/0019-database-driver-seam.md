# 0019. One schema, two SQLite drivers

- **Status:** Accepted (refines [0004](0004-sqlite-drizzle.md))
- **Date:** 2026-10-19

## Context
[0004](0004-sqlite-drizzle.md) chose SQLite with `better-sqlite3` and Drizzle. The server runs on Node ([0003](0003-server-runtime-custom-entry.md)), but tests run under `bun test` ([0002](0002-bun-monorepo-multiple-apps.md)).

What the documentation says (checked 2026-10-20):
- **Bun** ships a native, synchronous SQLite driver, `bun:sqlite`, whose API follows `better-sqlite3`'s ([Bun › SQLite](https://bun.com/docs/runtime/sqlite)). `better-sqlite3` itself is a native Node addon built for a specific Node ABI.
- **Node** has a built-in `node:sqlite`, which would serve both runtimes with no native addon, and Bun lists it as fully implemented ([Bun › Node.js compatibility](https://bun.com/docs/runtime/nodejs-compat)). But Node marks it **Stability 1.2, release candidate**, not stable ([Node.js › SQLite](https://nodejs.org/api/sqlite.html)).
- **Drizzle** supports `node:sqlite` only in its 1.0 release candidate ([Drizzle › node:sqlite](https://orm.drizzle.team/docs/sqlite/connect-node-sqlite)), and drizzle-kit's support for it has an open bug ([drizzle-orm#5471](https://github.com/drizzle-team/drizzle-orm/issues/5471)). The stable Drizzle line (0.45) supports `bun:sqlite` and `better-sqlite3`.

## Decision
- `@highsea/db` opens a database through a small driver seam: `bun:sqlite` (with `drizzle-orm/bun-sqlite`) under Bun, `better-sqlite3` (with `drizzle-orm/better-sqlite3`) under Node. Both are synchronous, so the Drizzle code is the same.
- The schema and the migrations are shared. Migrations are SQL files generated by drizzle-kit, embedded into a TypeScript module by a script (a test fails when it's stale), and applied by our own small migrator. Nothing reads migration files from disk at run time, so bundling and the Docker image don't need to carry them.
- Before applying migrations to an existing database, the server copies it with `VACUUM INTO` into `/config/backups/`, which SQLite documents as a way to make a consistent backup of a live database ([VACUUM](https://www.sqlite.org/lang_vacuum.html)).
- Every connection sets `journal_mode=WAL`, `foreign_keys=ON`, `synchronous=NORMAL` and a busy timeout. SQLite documents WAL with `synchronous=NORMAL` as "the best balance between performance and safety for most applications": always consistent and safe from corruption, though a commit in the last moments before a power loss can roll back ([PRAGMA synchronous](https://www.sqlite.org/pragma.html#pragma_synchronous)). Every job is idempotent ([0022](0022-job-queue.md)) and the torrent engine re-verifies on resume, so that loss is recoverable.

## Revisit
When `node:sqlite` reaches Stability 2 in Node's docs and Drizzle 1.0 is released with drizzle-kit support for it, move both runtimes to `node:sqlite` and drop the seam and the native addon.

## Consequences
- Tests are fast and need no native build; production keeps `better-sqlite3`.
- SQL that behaves differently between the two drivers would be a bug in only one place. Integration tests also run under Node in CI to catch that.
