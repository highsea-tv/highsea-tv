Written for highsea 0.1.0.

The status at the top of **Settings › VPN**, and the checks beneath it, say what's wrong. Each heading below is a message you may see there.

## highsea is on host networking

The built-in VPN won't start the tunnel while highsea's container shares the host's network, since the tunnel's interface and routes would land there. Copy the lines from **Compose for the built-in VPN**, put them in place of `network_mode: host` in highsea's service, and recreate the container. See [What it needs](/settings/vpn/connects/#what-it-needs).

## highsea can't run the tunnel yet

highsea's container is missing the NET_ADMIN capability. If you installed highsea from Package Center, TrueNAS's Apps or the Umbrel App Store, update it there: the update recreates the container with the capability. On CasaOS, add NET_ADMIN under **Capabilities** in highsea's settings; on Unraid, add `--cap-add=NET_ADMIN` to **Extra Parameters**. Otherwise copy the lines from **Compose for the built-in VPN**, which add `cap_add: [NET_ADMIN]`, into highsea's service and recreate the container. See [What it needs](/settings/vpn/connects/#what-it-needs).

## The kernel has no WireGuard, and there's no /dev/net/tun

Common on older NAS kernels, which have no WireGuard of their own, so highsea runs wireguard-go, which needs the TUN device. Add `devices: [/dev/net/tun:/dev/net/tun]` to highsea's service and recreate the container. If you installed highsea from Package Center, update it there: the update gives highsea a TUN device of its own.

## wireguard-go isn't allowed to open /dev/net/tun

The device is there, but highsea's user can't open it: the host's `/dev/net/tun` is often root's alone. In highsea's service, put `device_cgroup_rules: ["c 10:200 rwm"]` in place of the `/dev/net/tun` device and recreate the container: highsea then makes a TUN device of its own that it can open. If you installed highsea from Package Center, update it there instead.

## The host hasn't loaded the tun module

The device is there, but nothing answers behind it until the host loads its tun module. Load it on the host (`modprobe tun`) and restart highsea. On a Synology NAS, a package can't load it, so DSM needs a task that does: see [The built-in VPN](/install/synology/#the-built-in-vpn).

## Downloads say Waiting for the VPN

While the built-in VPN is set up but its tunnel isn't up, torrents wait rather than use your own connection, and Downloads, the Queue widget and the film's page say **Waiting for the VPN.** They carry on by themselves when the tunnel comes back, and the wait never counts as a stalled download.

## The built-in VPN runs on Linux

highsea isn't running in its Docker image or on Linux. Use [a VPN container](/settings/vpn/container/) or [an interface on this machine](/settings/vpn/interface/) instead.

## Names are being looked up outside the tunnel

The WireGuard file has no `DNS` line. Download a new file from your provider, or add the DNS server your provider documents, and upload it again. See [What the configuration file needs](/settings/vpn/connects/#what-the-configuration-file-needs).

## PIA didn't accept that username and password

Use the username you sign in to PIA with, which starts with `p`, not your email address.

## Couldn't reach the VPN container's control server

Check that gluetun is running, that highsea uses `network_mode: "service:gluetun"`, and that the address is `http://127.0.0.1:8000`.

## gluetun's control server refused that API key

The key in Settings › VPN must match the one in gluetun's `HTTP_CONTROL_SERVER_AUTH_DEFAULT_ROLE`. Recreate the gluetun container after changing it.

## Couldn't check the exit address

The IP echo service didn't answer. This isn't a leak; highsea checks again in 5 minutes.

## Your provider didn't forward a port

Downloads still work, with fewer peers able to reach you. For Proton VPN, make sure the configuration is for a P2P server with NAT-PMP turned on. See [Port forwarding](/settings/vpn/port-forwarding/).
