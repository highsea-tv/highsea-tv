Written for highsea 0.1.0.

**Settings › VPN** decides how torrents reach the internet. With a VPN, peers in a swarm see your provider's address instead of yours, and highsea checks that it stays that way. With highsea connects or an interface, only torrents use the VPN, and indexer searches if you choose. With a VPN container, everything highsea does goes through it, since highsea shares the container's network.

Only the Owner sees this area. Admins don't find it in Settings.

[Recommended setup](/recommended-setup/) has the short version. This page covers each mode, the providers, port forwarding, the checks and what to do when something goes wrong.

## The page

The page has three parts:

- **Status**: what the VPN is doing now, the checks that prove it, and **Check now** and **Reconnect**.
- **Connection**: the mode, and what that mode needs.
- **Behaviour**: what highsea does with the tunnel. It's hidden while the mode is **Off**.

Changes take effect when you press **Save**.

## Choosing a mode

| Mode | What it does | Suits |
| --- | --- | --- |
| **highsea connects** (Recommended) | highsea runs its own WireGuard tunnel to your provider. Only torrents use it, and they can't leave outside it. | Linux, with a provider that offers WireGuard |
| **A VPN container** | highsea shares a gluetun container's network and reads its status and forwarded port. | Providers that only offer OpenVPN, or if you already run gluetun |
| **An interface on this machine** | Torrents are bound to a tunnel you run yourself. Your system's routing decides the path. | A VPN you already run on the host |
| **Off** | Torrents use your own connection. Anyone in the swarm can see your address. | Testing, or where a VPN isn't wanted |

A new server starts with **Off**.

## highsea connects

highsea brings up a WireGuard tunnel inside its own container and binds every torrent to the tunnel's address. A packet from that address can only leave through the tunnel, so if the tunnel drops, torrents stop rather than fall back to your own connection.

### What it needs

- **Linux.** highsea's Docker image runs Linux, so this works wherever highsea runs in Docker. If you run highsea some other way on macOS or Windows, use another mode.
- **The NET_ADMIN capability** for highsea's container, so it can make its own network interface and routes. This reaches only highsea's container, not the host.
- **Its own network**, not host networking. With host networking, highsea's interface and routes would land in the host's network beside everything else.
- **The TUN device**, only on older kernels without WireGuard built in (Linux before 5.6, which some NAS systems still run).

`compose.connects.yaml` at the root of highsea's repository has all of this. The lines that matter:

```yaml title="compose.yaml"
services:
  highsea:
    image: ghcr.io/highsea-tv/highsea:latest
    cap_add: [NET_ADMIN]
    # devices: [/dev/net/tun:/dev/net/tun]   # only on a kernel without WireGuard
    ports:
      - "3000:3000"
      - "6881:6881/tcp"
      - "6881:6881/udp"
      - "7368:7368/udp"
```

Because the container doesn't use host networking, apps on your network find the server through the UDP broadcast on port 7368 rather than mDNS. See [Network and remote access](/settings/network/).

If highsea starts without the capability, the status says **highsea can't run the tunnel yet** and shows the compose lines to add, with a **Copy** button. Add them, then recreate the container.

### Pick your provider

Choose your provider under **Provider**. highsea shows that provider's own steps beneath it. Most providers give you a WireGuard configuration file to download; upload it with **Upload a file**, or choose **Paste instead** and paste its contents. Once saved, the file's keys stay on the server: the page shows only the file's name, with **Replace the file** to change it.

| Provider | How highsea connects | Port forwarding |
| --- | --- | --- |
| Proton VPN | A WireGuard file from Downloads › WireGuard configuration, on a server marked P2P with NAT-PMP (port forwarding) turned on | Automatic |
| Private Internet Access | Your PIA username and password, and a **Region**. highsea registers its own WireGuard key with PIA, so there's no file. | Automatic |
| AirVPN | A WireGuard file from Client Area › Config Generator (Linux, WireGuard) | A port you reserve under Client Area › Forwarded ports, typed into **Forwarded port** |
| Mullvad | A WireGuard file from your account's WireGuard configuration page | None: Mullvad stopped offering it |
| IVPN | A WireGuard file from the Client Area's WireGuard configuration generator | None: IVPN stopped offering it |
| Windscribe | A WireGuard file from My Account › Config Generator › WireGuard (paid accounts) | An ephemeral port with Matching Port from My Account › Port Forwarding, typed into **Forwarded port**. It lasts 7 days, so request a new one and update the field when it runs out. |
| Surfshark | A WireGuard file from VPN › Manual setup › WireGuard | None |
| Another WireGuard provider | Any WireGuard configuration file | A port typed into **Forwarded port**, if your provider gives you one |

The list of providers comes from highsea's catalog, so new providers can appear without a new version of highsea.

### What the configuration file needs

highsea reads the file as WireGuard's own tools do, and refuses one it can't use, with the reason under the field. Besides its keys and at least one `[Peer]`, the file needs:

- an IPv4 `Address` in its `[Interface]` section;
- an `Endpoint` for each `[Peer]`;
- a `DNS` line in its `[Interface]` section. Without it, tracker names would be looked up outside the tunnel, so highsea stops torrents and the **Names** check says so.

Files downloaded from the providers above have all three.

highsea connects carries IPv4 only for now, so torrents use IPv4 while it's on.

## A VPN container

highsea joins the network of a [gluetun](https://github.com/qdm12/gluetun-wiki) container, whose only route out is the tunnel. gluetun makes the tunnel and supports many providers, including those that only offer OpenVPN; highsea reads gluetun's status and forwarded port from its control server.

### Set it up

1. Make an API key for gluetun's control server:

   ```sh
   docker run --rm qmcgaw/gluetun genkey
   ```

2. Add a gluetun service to your compose file and join highsea to its network with `network_mode: "service:gluetun"`. highsea's ports move to the gluetun service, since highsea no longer has a network of its own. `compose.gluetun.yaml` at the root of highsea's repository is a complete example for Proton VPN.

   For other providers, open **Compose for your provider** on the VPN page, pick your provider, and **Copy** the block it writes. Fill in what your provider gives you, and put your API key in `HTTP_CONTROL_SERVER_AUTH_DEFAULT_ROLE`. gluetun's wiki has a page for each provider with the settings it takes. highsea never gets access to Docker itself, so you run this step.

3. Start both, then in **Settings › VPN** choose **A VPN container**.
4. Leave **Control server** at `http://127.0.0.1:8000`. The two containers share a network, so gluetun is on highsea's own loopback address.
5. Enter the **API key** and save. highsea asks gluetun before it saves, and says so if gluetun refuses the key or can't be reached.

For port forwarding through gluetun, turn it on in gluetun's settings (`VPN_PORT_FORWARDING: "on"` for providers gluetun supports it with) and keep **Use the forwarded port** on in highsea.

Apps can't find the server on their own in this setup, since discovery needs host networking or highsea's own published ports. Give them the server's address instead.

## An interface on this machine

If you already run a VPN on the host, such as WireGuard or OpenVPN, choose **An interface on this machine** and pick its **Interface**. The list shows the interfaces highsea can see besides the LAN, with their addresses. In Docker, highsea sees the host's interfaces only with host networking.

highsea binds every torrent to the interface's address. If the interface goes down or loses its address, torrents stop at once and start again when it's back. Your system's routing still decides the path, so highsea can promise less here than in the other two modes; the **Kill switch** check says so.

Port forwarding is up to you in this mode: forward the torrent port through your tunnel yourself, if your provider allows it.

## Behaviour

| Setting | What it does |
| --- | --- |
| **Stop torrents when the VPN is down** | Always on, in every mode with a VPN. highsea connects: a packet from the tunnel's address can't leave any other way. A VPN container: it has no other route. An interface: torrents stop the moment the interface or its address goes. |
| **Use the forwarded port** | Torrents listen on the port your provider forwards, and tell trackers when it changes. Shown for a VPN container, and for highsea connects with a provider that forwards ports. On by default. |
| **Send indexer searches through the VPN too** | Off by default. A private tracker's account is often tied to your own address, and searches would fail while the tunnel is down. Turn it on if you'd rather your indexers never see your own address. |

## Port forwarding

Without a forwarded port, downloads still work: highsea connects out to peers. With one, peers can connect in too, so more peers can reach you, which helps with less popular torrents and with seeding.

- **Proton VPN** and **Private Internet Access**: highsea asks the provider for a port once connected, keeps it renewed, and moves torrents to it. If the provider doesn't forward one, highsea tries again every minute and the check warns.
- **AirVPN**, **Windscribe** and **Another WireGuard provider**: reserve a port with your provider and type it into **Forwarded port**. Leave the field empty if there isn't one.
- **Mullvad**, **IVPN** and **Surfshark** don't forward ports.
- **A VPN container**: highsea uses the port gluetun reports.

## Status and checks

The top of the page says what the VPN is doing:

| Status | Meaning |
| --- | --- |
| **No VPN** | The mode is Off. Torrents use your own connection. |
| **Connecting to** your provider | Torrents wait until the tunnel is up. |
| **Connected through** your provider (or **Bound to** an interface) | Torrents leave through the tunnel, from the address shown. |
| Your provider **is down** | Torrents are stopped until the tunnel is back. Nothing leaks onto your own connection. |
| **Couldn't connect** | The reason is shown beneath, such as a refused password or a bad configuration. |

When the tunnel drops, highsea reconnects on its own, waiting a little longer after each try, up to 5 minutes between tries. **Reconnect** tries at once.

Below the status is a list of checks, each marked Passed, Warning, Failed, Note or Waiting:

| Check | What it looks at |
| --- | --- |
| **Tunnel** | Whether the tunnel is up. For highsea connects, the time since the last WireGuard handshake; no handshake for 3 minutes counts as down. |
| **Exit address** | The address torrents leave from, asked of an IP echo service through the tunnel, and compared with your own. |
| **Names** | Whether tracker names are looked up through the tunnel. |
| **Kill switch** | Whether anything could leave outside the tunnel. |
| **Port forwarding** | The forwarded port and how many peers have connected in, or why there isn't one. |
| **IPv6** | Whether IPv6 goes through the tunnel, or torrents use IPv4 only. |

The checks run when the tunnel connects, every 5 minutes after that, after each reconnect, and when you press **Check now**. Torrents only start once the first checks are done.

With highsea connects, a check that finds a leak stops torrents: an exit address that's your own, names looked up outside the tunnel, or a missing routing rule (which highsea puts back first). In the other modes a failing check warns, since the container has no other route and the interface binding already holds.

When the VPN is down or a check fails, **System › Health** says so too, and a connection that hears **Health** sends it to you. See [Notifications](/settings/notifications/).

## Troubleshooting

**highsea can't run the tunnel yet.** highsea's container is missing the NET_ADMIN capability. Add `cap_add: [NET_ADMIN]` to its service and recreate the container.

**The kernel has no WireGuard, and /dev/net/tun isn't there.** Common on older NAS kernels. Add `devices: [/dev/net/tun:/dev/net/tun]` to highsea's service and recreate the container.

**highsea connects runs on Linux.** highsea isn't running in its Docker image or on Linux. Use a VPN container or an interface on this machine instead.

**Names are being looked up outside the tunnel.** The WireGuard file has no `DNS` line. Download a new file from your provider, or add the DNS server your provider documents, and upload it again.

**PIA didn't accept that username and password.** Use the username you sign in to PIA with, which starts with `p`, not your email address.

**Couldn't reach the VPN container's control server.** Check that gluetun is running, that highsea uses `network_mode: "service:gluetun"`, and that the address is `http://127.0.0.1:8000`.

**gluetun's control server refused that API key.** The key in Settings › VPN must match the one in gluetun's `HTTP_CONTROL_SERVER_AUTH_DEFAULT_ROLE`. Recreate the gluetun container after changing it.

**Couldn't check the exit address.** The IP echo service didn't answer. This isn't a leak; highsea checks again in 5 minutes.

**Your provider didn't forward a port.** Downloads still work, with fewer peers able to reach you. For Proton VPN, make sure the configuration is for a P2P server with NAT-PMP turned on.
